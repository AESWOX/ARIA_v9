# Технический аудит ARIA v9 (аудит с контекстом)

Дата: 19.10.2026. Ревизия: `origin/main` = `90d33ed`.

**Статус документа.** Аудит выполнен ассистентом, который перед этим читал документацию проекта. Это не независимый аудит: независимый проводится по `docs/AUDIT_BRIEF.md` другим исполнителем без документов. Здесь собраны находки по трём темам: сжатие контекста, аудит внутри системы (включая рой саб-агентов), задержки и точность ответов.

**Метки доказательности.**
- **[код]** — прочитано в исходниках, файл и функция указаны.
- **[лог]** — подтверждено серверными логами владельца (12–17.10) или выводом его прогонов.
- **[гипотеза]** — правдоподобно по коду и данным, но не измерено; требует проверки.

Критичность: High — прямо влияет на корректность или заметную задержку; Medium — ухудшает качество или надёжность при условиях; Low — гигиена.

## 1. Главное

1. Качество сжатия контекста никем не измеряется, и на настоящих длинных чатах оно **ни разу не срабатывало** в наблюдаемых логах (K0, K7).
2. Сжатие стоит на критическом пути ответа с таймаутом до 120 с на попытку (K8), зависит только от Gemini (K1) и принимает пустую сводку (K2).
3. Аудит внутри системы смотрит на вызовы инструментов, а не на «запрос против результата»: исходный запрос, уточнения, допущения и итоговый ответ в него не передаются (A1). Работу саб-агентов он принимает по самоотчёту (A7).
4. Аудит даёт ложные отказы при исправленных ошибках (A3) и слабый «pass» по подстроке (A2), а точность измерить нечем (A6).
5. Задержки: нестабильные бесплатные провайдеры (за три дня 348 ответов 503 и 161 ответ 429), фиксированный таймаут 60 с на звено, нет разбивки времени по этапам (раздел 4).

## 4. Задержки и точность ответов

Данные владельца: смоук `chat` занимал 4,1–77,2 с (7 прогонов, 15–18.10), `ctx` — 21,6–206,2 с. Разброс 10-кратный. Причина по этапам не измерена.

| ID | Крит. | Находка | Метка |
|----|-------|---------|-------|
| L1 | High | Провайдеры нестабильны: за 12–15.10 (события посчитаны по строкам провайдера, по одной на ответ) 348 ответов 503 и 161 ответ 429 (почти все у вариантов Gemini), 49 ответов 402 (DeepSeek, баланс), 12 ответов 404, 10 таймаутов, 259 переключений провайдера. Каждый сбой стоит времени: повтор при 5xx с паузой 1 с и 2 с, затем переход к следующему звену | [лог], [код] |
| L2 | High | Таймаут запроса к звену фиксирован: 60 с (`timeout_sec=60`). Зависший провайдер держит ход минуту, цепочка из N звеньев при таймаутах даёт N × 60 с | [код], [лог] (10 таймаутов) |
| L3 | Medium | Проверка доступности: кэшируется только успех; для недоступного провайдера на каждый запрос две попытки по 2 с | [код] |
| L4 | Medium | Сжатие на критическом пути хода (K8) | [код] |
| L5 | Medium | Аудит и повторы (A3, A5) умножают время задачи | [код] |
| L6 | Medium | Рассуждающие модели: `deepseek_reasoner_thinking = "high"` по умолчанию; для служебных вызовов (аудитор, кларифайер, сжатие) нет бюджета времени | [код] |
| L7 | Medium | Опрос интерфейса: пока чат занят, UI примерно каждые 2 с запрашивает `/sessions/{id}/run`, `/chat/sessions/{id}/messages`, `/chat/sessions`. Это нагрузка на SQLite и источник конкуренции за базу | [лог], [гипотеза] о вкладе в блокировки |
| L8 | High | Нет разбивки времени по этапам (выбор провайдера, попытки, сжатие, аудит, инструменты, делегирование). Есть `duration_ms` у вызовов инструментов; аналитика считает токены приблизительно и не учитывает токены кэша и реальную стоимость (`actual_cost=0`). Из-за этого причины задержек приходится угадывать | [код] |
| L9 | Low | В `http_utils.py` зашиты значения `median_duration_ms: 920`, `p95_duration_ms: 1800` (похоже на пример ответа): проверить, не показываются ли пользователю как реальные | [код] |

Точность ответов: при отказе сильного звена цепочка отдаёт запрос более слабой модели («degraded»). Как часто это происходит и как это меняет качество, не измерено; логи показывают 259 переключений провайдера за три дня.

## 5. Что сделано хорошо

- Сжатие вынесено из транзакции БД на время сети, оригиналы сообщений не удаляются (`compressed_out`), защищены начало, хвост и текущий ход, нет сжатия при ожидании подтверждения.
- В аудите сначала детерминированные проверки по фактам, затем модель; структурный провал не отменяется мнением модели (`merge_statuses`).
- Есть детекторы целостности без LLM (`integrity.py`) и честный вердикт `unaudited` вместо маскировки отсутствия аудита.
- Цепочки провайдеров с карантином, пустой ответ считается отказом звена.

## 6. Чего этот аудит не охватывает

Безопасность (отдельный независимый аудит), содержимое `loop.py` целиком (рассмотрены места вызова сжатия и аудита), поведение на длинных живых диалогах (нет данных), поведение рой-режима под нагрузкой, UI. Все пункты с меткой [гипотеза] требуют измерения, план измерений: `docs/PLAN_AUDITORS_AND_COMPRESSION.md`, фаза 0.

## 7. Быстрая проверка по своему логу (PowerShell)

```powershell
$log = "$env:APPDATA\ARIA\logs\backend.log"
Select-String $log -Pattern "compression failed","compressed \d+ messages","switching provider","HTTP 402","HTTP 429","HTTP 503","ReadTimeout","database is locked" |
  Group-Object { $_.Pattern } | Select-Object Name, Count
```

Если «compressed N messages» встречается только с N равным 1–3, сжатие на реальных диалогах не работает (K0).
