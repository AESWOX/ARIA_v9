# Авторство и история git: правила и порядок работы

## 1. Правило

- Автор и коммиттер каждого коммита — владелец репозитория. Допустимые адреса перечислены в `.github/allowed_authors.txt`.
- Соавторы (включая любые инструменты и ассистентов) в сообщениях коммитов не указываются: трейлер `Co-authored-by` и пометки вида «generated with …» в историю не попадают.
- Лицензии и уведомления сторонних компонентов (в том числе вендоренный `desktop/src/components/vendor/nous-ui`) не удаляются. Поддержка внешних LLM-провайдеров в самом продукте не затрагивается: это функции приложения, не авторство.

## 2. Как правило обеспечено для новых коммитов

| Механизм | Файл | Что делает |
|----------|------|------------|
| Хук `commit-msg` | `.githooks/commit-msg` | вырезает строки `Co-authored-by` и пометки инструментов из сообщения перед созданием коммита |
| Проверка в CI | `scripts/check_authorship.py`, `.github/workflows/authorship.yml` | падает, если у коммита автор/коммиттер вне списка или в сообщении есть `Co-authored-by` |
| Тесты | `backend/tests/test_check_authorship.py` | проверяют скрипт и хук на временном репозитории |

Включить хук (один раз на каждый клон):

```powershell
git config core.hooksPath .githooks
git config user.name  "AESWOX"
git config user.email "164995783+AESWOX@users.noreply.github.com"
```

Git for Windows запускает хук через встроенный `sh`. Проверить вручную: `python scripts/check_authorship.py origin/main..HEAD`.

Если коммиты создаёт ассистент или другая программа, в её настройках отключают добавление соавтора и подпись в сообщении. Хук и CI-проверка страхуют, если настройку забыли.

## 3. Переписывание уже существующей истории

Переписывание заменяет автора и коммиттера во всех коммитах всех веток и вырезает трейлеры соавторства из сообщений. **Содержимое файлов не меняется** (деревья коммитов остаются идентичными), меняются только метаданные и, как следствие, хеши всех коммитов.

Набор для переписи лежит **вне репозитория** (`rewrite_history.ps1`): в нём перечислены старые идентификаторы, и хранить их в репозитории означало бы сохранить то, что удаляется. Порядок:

1. Дождаться, пока `fix/clarify-round2` смержена в `main` и ручной сценарий пройден: история будет переписываться один раз.
2. Запустить `rewrite_history.ps1` **без** `-Push`: скрипт делает зеркальную копию-бэкап, чистый клон, переписывает историю и печатает проверки (число идентичностей, число трейлеров, совпадение деревьев).
3. Если проверки в порядке, запустить с `-Push` (требует ввода слова `REWRITE`): выполняется `git push --force` для веток и тегов.
4. На всех своих машинах заново клонировать репозиторий или выполнить `git fetch origin` и `git reset --hard origin/main`.

Ограничения, которые нужно знать заранее:

- Защита веток на GitHub (если включена для `main`) блокирует force-push: на время переписи её отключают.
- Старые коммиты остаются на GitHub, пока доступны по ссылкам `refs/pull/*` (PR #1 и #2), по прямым SHA, в форках и в чужих клонах. Полное удаление даёт только новый репозиторий с переписанной историей (теряются PR, issues, релизы) или обращение в поддержку GitHub.
- Файлы релизов (`latest.json` для автообновления) не затрагиваются, но если репозиторий пересоздаётся или переименовывается, нужно обновить `endpoints` в `desktop/src-tauri/tauri.conf.json` и заново загрузить релизы.
- Резервная зеркальная копия, которую делает скрипт, сохраняет старую историю. Удалить её нужно самому, когда переписанный репозиторий проверен.
- В списке старых адресов есть один личный адрес (`gmail`). Скрипт спрашивает, принадлежит ли он владельцу; если нет, его строка исключается из замены, и тогда CI-проверка авторства на первом пуше сообщит об этом коммите.
