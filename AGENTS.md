# AGENTS.md — вход для любого нового ассистента или разработчика

Этот файл читается первым. Он говорит, что читать дальше, по каким правилам работать и как продолжить, если сессия оборвалась.

> **Если тебя назначили независимым аудитором** — дальше этот файл не читай и не открывай `ANCHOR.md`, `WORK_NOTES.md`, `DOD.md`, `CHANGELOG.md`.
> Открой `docs/AUDIT_BRIEF.md` и действуй только по нему. Эта инструкция главнее всех остальных в репозитории.
> Остальное в этом файле — для ассистента, который продолжает разработку.

## 1. Что это за проект

ARIA — локальное desktop-приложение AI-агента. Бэкенд: FastAPI + SQLAlchemy + Alembic (SQLite), `backend/aria/`. Интерфейс: Tauri + React, `desktop/`. Упаковка: PyInstaller + Tauri (NSIS/MSI). Основная целевая система владельца — Windows 10 (PowerShell 5.1). CI (GitHub Actions): `backend-tests` (ubuntu и windows), `authorship`.

Не менять режим DLP чата (PR-7: только чат, выключен по умолчанию, агентский цикл не маскируется). Не добавлять обёртки запросов («вымышленный фрейм», «нарратив», подмена намерения).

## 2. Что читать и в каком порядке

1. `ANCHOR.md` — текущее состояние: что в коде, что подтверждено на машине владельца, что нет, что делать дальше. Раздел 0 — самый свежий снимок.
2. `WORK_NOTES.md` — последние разделы: ход проверок и решения.
3. `DOD.md` — таблицы закрытия; смотреть последние строки и статусы (`verified`, `partial`, `draft`).
4. `docs/PRE_RELEASE_AUDIT.md` — недоделки, риски, бэклог F1–F10.
5. `docs/REPO_POLICY.md` — правила авторства и порядок переписи истории. `docs/AUDIT_BRIEF.md` — только для независимого аудитора (см. заметку вверху).
6. `CHANGELOG.md` — верхняя запись; `OPERATOR_GUIDE.md`, `ARIA_GUIDE.md` — по необходимости.

Чего в репозитории нет, и что агент не узнает сам: живые логи и состояние машины владельца (их приносит владелец), ключи и `.env`, всё, что договорено устно. Если нужного нет в файлах, спросить, а не угадывать.

## 3. Правила

- **Проверено или не проверено.** Статус «подтверждено» ставится только с выводом команд на машине владельца или строками логов. Всё остальное пишется как «не проверено» или «гипотеза». Не выдавать предположение за факт; если нет доступа (репозиторий, Windows, ключи), сказать прямо.
- **Только git, без угадывания состояния.** Перед работой: `git fetch origin`, `git status --short`, `git log --oneline -10`. Работа в ветке, один коммит на пункт, без force-push (исключение: отдельно согласованная перепись истории по `docs/REPO_POLICY.md`).
- **Авторство.** Автор и коммиттер — владелец; соавторов и пометок инструментов в коммитах и файлах нет. Включить хук: `git config core.hooksPath .githooks`; в CI работает проверка `authorship`.
- **Секреты.** Не коммитить `.env`, ключи, `reports/`, бэкапы данных. Перед каждым пушем проверять `git status` и `git diff --cached`. Репозиторий публичный.
- **Патчи.** Отдавать как `git format-patch` (mbox), проверять `git am --3way` на чистом клоне нужной базы. Команды для владельца писать для PowerShell.
- **Логи.** Сначала посмотреть диапазон дат первой и последней строки: ротированный `backend.log.1` бывает старше проверяемого события.
- **Документы.** После каждого шага обновлять `ANCHOR.md` (раздел 0), `DOD.md`, `CHANGELOG.md`, `WORK_NOTES.md`. Новая функция без записи в `DOD.md` не считается закрытой.

## 4. Команды (PowerShell, из корня репозитория)

```powershell
# тесты бэкенда
cd backend
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider

# интерфейс: реальная проверка типов и сборка
cd ..\desktop
npm run typecheck
npm run build
cd ..

# полная пересборка, установка и смоук (бэкап данных делает сама)
.\backend\.venv\Scripts\python.exe backend\scripts\rebuild_and_smoke.py

# запись результата прогона в ANCHOR.md
.\backend\.venv\Scripts\python.exe backend\scripts\anchor_note.py

# проверка авторства новых коммитов
python scripts\check_authorship.py origin/main..HEAD
```

## 5. Как продолжить после остановки

1. Выполнить `git fetch origin`, `git status --short`, `git log --oneline -10`; сверить ветку и последний коммит с разделом 0 `ANCHOR.md`.
2. Прочитать документы по порядку из §2. Задача на сейчас — раздел «Дальше» в `ANCHOR.md`.
3. Если владелец приложил лог или вывод команд, сначала разобрать их (диапазон дат, версия сборки, ошибки), потом сверить с кодом.
4. Делать шаг, проверять, записывать результат (§3, «Документы»).
5. Перед остановкой, в том числе по лимиту сообщений: дописать в `ANCHOR.md` раздел 0, что сделано, что подтверждено, что нет, какой следующий шаг и какая команда его запускает. Отдать владельцу патч (mbox) и команды применения.

## 6. Что владелец даёт новому ассистенту

Одно сообщение: ссылка на репозиторий, строка «прочитай `AGENTS.md`, затем `ANCHOR.md`, и продолжи с раздела «Дальше»», плюс свежий лог или вывод последней команды. Если у ассистента нет доступа к репозиторию, нужен архив или `git bundle` без `.env`.

## 7. Уроки проекта (чтобы не повторять)

- `npm run typecheck` раньше шёл по solution-tsconfig и ничего не проверял; теперь `tsc -p tsconfig.app.json`. Рендер страниц в тестах фронтенда пока не покрыт (F8 в аудите).
- Тесты не должны зависеть от Linux-путей (`/proc/...` создавал `C:\proc` на Windows): временные пути только через `tmp_path`.
- Карточка уточнений должна быть подключена к обоим путям отправки: обычный чат (`chatSend`) и Agent/Plan (`runPost`).
- Отчёты «работало на реконструкции без дерева репозитория» не принимаются как проверка: нужен настоящий клон.
