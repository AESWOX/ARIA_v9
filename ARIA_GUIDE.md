## 1. Что это за продукт, в одной картинке

ARIA — десктопное приложение: окно на Tauri + React, внутри которого живёт Python-сервер (FastAPI), собранный в `backend.exe`. Окно запускает сервер как «сайдкар», сервер хранит всё в SQLite, ходит к облачным LLM и ведёт заметки в папке, совместимой с Obsidian.

```
┌──────────────── Окно (Tauri + React, WebView2) ────────────────┐
│ Страницы: Chat, Sessions, Notes, Skills, Cron, Models, Env,    │
│ Logs, Files, MCP, Plugins, Channels, Pairing, Webhooks ...     │
└───────────────▲──────────────────────────────┬─────────────────┘
        WebSocket /api/ws (события)            │ HTTP /api/*  (токен в заголовке)
┌───────────────┴──────────────────────────────▼─────────────────┐
│ backend.exe  (FastAPI, порт выбирается Tauri, токен — на запуск)│
│  routers/ ─► core/ (loop, executor, audit, integrity, roles)    │
│              ├─► tools/ (19 тулов) ─► shell, файлы, vault, web  │
│              ├─► llm/ (router + пул ключей + бюджет)            │
│              └─► db/ (SQLite, 18 таблиц, alembic)               │
└───────────┬───────────────────────────────┬────────────────────┘
            │                               │
   Облачные LLM (DeepSeek,           Obsidian-vault (папка .md),
   Gemini, Groq)                     skills (папки с SKILL.md)
```

Процессы `[проверено 09.10]`: установленное приложение — цепочка `local-agent-ui.exe` → `backend.exe` → `backend.exe` (onefile PyInstaller: загрузчик + дочерний), после закрытия окна процессов не остаётся. Tauri-оболочка `[проверено]` умеет: выбрать свободный порт, сгенерировать токен, запустить сайдкар, дождаться `/status`, **перезапускать его при падении**, убивать зомби-процесс прошлого запуска, не пускать вторую копию (`single-instance`), обновляться (`updater` с публичным ключом и адресом `github.com/AESWOX/ARIA_v9/releases/latest/download/latest.json`). Чего нет: трея, автозапуска, глобальной горячей клавиши, режима «окно закрыто, сервер работает».

## 2. Идея ядра: «цикл с проверкой честности» (из ТЗ)

Самое ценное в репо — не интерфейс, а замысел из `ARIA_FULL_TZ_v1.md`: агент не имеет права просто сказать «готово». Каждый результат проверяется.

```
Запрос → 1 Vault-check → 2 План → 3 Исполнение → 4 Аудит → 5 Хуки → 6 Повтор? → 7 Доставка
                                                      │
                          аудит корректности + аудит честности (без LLM):
                          НАЕБАЛ  — заявил успех, которого не было
                          ПРОЕБАЛ — честно попытался и не вышло
                          ЗАБЫЛ   — не закрыл пункт плана
```

Что из этого реально написано `[проверено]`:

| Компонент | Файл | Что делает |
|---|---|---|
| Исполнитель Stage 1–7 | `core/executor.py` (916 строк) | План (Oracle) → шаги → аудит → хуки → доставка в vault |
| Аудит честности | `core/integrity.py` | Чистые функции: хэш файла до/после, exit-code, junit-артефакт, покрытие шагов плана |
| Аудит корректности | `core/audit.py` | Структурная проверка тул-вызовов + проверка ролью `qa_auditor` |
| Валидатор плана | `core/plan_validator.py` | Шаг без `tool_ref`/`skill_ref` не проходит; 3 плохих плана подряд = «Oracle НАЕБАЛ» |
| Анти-зацикливание | `core/guardrails.py` | Три детектора: одинаковая ошибка, один и тот же тул, нет прогресса |
| Блокировки | `core/locking.py` | Оптимистичная блокировка плана + файловый lock с TTL 30 с |
| Секрет-скан | `core/secretscanner.py` | Не даёт доставить результат с ключами |
| Подтверждения | `core/approvals.py` | Опасная команда или пишущий тул MCP → «внимание-карточка» → человек нажимает Approve/Reject; одобренное действие исполняется один раз и переживает перезапуск |
| Профиль запуска | `core/runprofile.py` | Выбор модели по местам (босс / сабы / аудитор), стиль solo/boss, уровень аудита, глубина мышления; хранится на сессию; правило «сабы не дороже босса» |
| Сжатие контекста | `llm/compression.py` | Когда оценка токенов истории сессии выше порога (100 000), середина истории заменяется сводкой (на своём месте), первые сообщения и текущий ход с результатами тулов остаются дословно; оригиналы в БД; при ожидающем Approve не сжимает; вызывается из `/chat` и из цикла агента |
| Импорт плагинов | `plugins/importer.py`, `routers/plugins.py` | Плагин формата Agent Plugins (папка, .zip или GitHub с ref) → скиллы `<плагин>-<скилл>` и MCP-серверы (всегда отключены, секреты не подставляются); `/plugins/preview`, `/plugins/import`, `GET /plugins`, `DELETE /plugins/{name}`; UI пока нет (патч 0013, на Windows не проверен) |
| Роли | `core/roles.py` | 16 ролей-пресетов (какие тулы, какая модель); 5 выключены |
| Делегирование | `core/delegate.py` | Саб-агент = рекурсивный вызов цикла; глубина 1, до 5 параллельно |
| Бюджет | `llm/router.py` | 80 % — предупреждение, 100 % — премиум-модели блокируются, запрос падает на бесплатные |
| Эскалация | `core/notifiers/telegram.py` | Исчерпаны 3 попытки или НАЕБАЛ → сообщение в Telegram |

**Вывод:** фундамент для «рой + честность + Telegram» уже заложен. Достраивать надо вокруг него, а не переписывать.

## 3. «Приколюхи»: что я нашёл и что это значит

Каждый пункт проверен по коду. Они объясняют, почему приложение выглядит готовым, а в работе ведёт себя странно.

### 3.1. Три двери для задачи, и главная — закрытая `[проверено]`

Запустить задачу можно тремя способами, и они делают разное:

| Путь | Что запускается | Кто им пользуется |
|---|---|---|
| `POST /sessions/{id}/messages`, `POST /tasks/{id}/start` | **ReAct-цикл** (`core/loop.py`): модель сама выбирает тулы, до 15 итераций, потом аудит | Страница Sessions |
| `POST /tasks/{id}/run-executor` | **Stage 1–7 из ТЗ** с аудитом честности | **Никто.** В `api.ts` такого вызова нет |
| `/api/chat/*` | Просто диалог с моделью **без тулов** | Страница Chat (`NativeChatPage`) |

То есть центральный механизм ТЗ (честность, план, интеграти-аудит) в приложении недостижим из интерфейса, а чат, которым вы будете пользоваться чаще всего, вообще не умеет действовать.

Дополнительно есть режим `codex` (запуск внешнего Codex CLI, выключен флагом `codex_enabled`) и режим `demo`.

### 3.2. Режим «демо» врёт об успехе `[проверено]`

В `routers/tasks.py` функция `_run_demo_task` пишет фейковый вызов тула, фейковый ответ «Задача выполнена в MVP-режиме» и ставит вердикт аудита `pass` от модели `stub-standard`. Сейчас она включается только явным `mode: "demo"`, но в проекте, где главная ценность — честность, такой код не должен существовать.

### 3.3. Тихие моки в боевом пути `[проверено]`

- `core/executor.py`: если роутера нет, план строится функцией `_mock_oracle_plan`, а тул-вызов подменяется выдуманным `exit_code: 0`.
- `llm/router.py`: если нет ни одного ключа, регистрируются `StubProvider`-ы, которые отвечают заглушкой. Задача формально «выполняется».
- Следствие `[вывод]`: на ноутбуке без настроенных ключей агент будет «работать» и рапортовать об успехе. Нужен честный отказ «нет провайдера».

### 3.4. Агент работает внутри HTTP-запроса `[проверено; частично исправлено в 0002+0003]`

*После 0003:* `POST /sessions/{id}/messages` и `/tasks/{id}/start` ставят задачу в `TaskRunner` и возвращают `queued`; результат приходит событиями WebSocket. Страницу Sessions на такой ответ я не проверял — это первое, что смотреть руками.


`post_message` делает `await execute_agent_loop(...)` прямо в обработчике запроса. Нет очереди, нет фонового исполнителя, нет возобновления после перезапуска, нет нормальной отмены. Для окна это терпимо, для Telegram, роя и расписаний — главное препятствие.

### 3.5. Расписания не исполняются `[проверено; исправлено в 0002+0003]`

*После патчей:* расписания исполняются через `TaskRunner`; новое расписание ждёт своего времени (не срабатывает на первом тике). Пропущенный при выключенном приложении запуск не догоняется, если расписание ни разу не запускалось.


Страница Cron хранит расписания в таблице, но в зависимостях нет ни одной библиотеки разбора cron, а фоновый цикл (`main.py`, раз в 120 с) вызывает только две жёстко прописанные служебные функции. Задача, которую вы создадите на «каждый день в 9:00», не сработает никогда. Кнопка «запустить сейчас» умеет запускать лишь эти две функции по имени.

### 3.6. Навыки и заметки не в git `[проверено]`

В `.gitignore` стоит `data/`, в репозитории 0 файлов из `backend/data`. Но:
- `backend.spec` требует папку `data/skills` (строка 12) для вшивания в exe;
- `RELEASE_MANIFEST.txt` включает `backend/data/vault/**` и `backend/data/skills/**`;
- по `MANIFEST.md` у вас 73 навыка и 179 заметок.

`[вывод]`: все они лежат только на вашем диске. Чистый клон соберёт приложение без навыков (или упадёт на сборке — зависит от версии PyInstaller). Резервной копии в git нет.

### 3.7. `shell_execute` — не песочница `[проверено; политика default-deny в 0002+0003]`

*После патчей:* команда выполняется без подтверждения, только если все сегменты — из allowlist, без inline-кода интерпретаторов, без `find -exec/-delete`, без путей и перенаправлений за пределы корня. Остальное — карточка Approve/Reject. Подтверждение передаёт система; значение `approved` из ответа модели игнорируется. Разрешённые `git`/`npm run`/`pytest` по-прежнему исполняют код проекта.


Команда выполняется через `create_subprocess_shell`, а «песочница» — это лишь рабочая папка. Команда может выйти из неё (`cd C:\ && ...`). Защита — чёрный список регулярных выражений на «опасные» команды, и аудит уже показал, что его обходят (`rm -fr`, `-Rf`, `--recursive`; исправлено патчем). Файловые тулы (`file_read/write/search`) защищены правильно: путь за пределами корня отклоняется. Для ассистента с доступом к вашему рабочему ноутбуку нужна политика «по умолчанию запрещено, разрешён список, остальное — через подтверждение».

### 3.8. Происхождение заглушек — Hermes `[проверено]`

В `WORK_NOTES.md` и `MANIFEST.md` видно: интерфейс унаследован от панели Hermes Agent (Nous Research; папка `components/vendor/nous-ui`). Все 66 заглушек — это кнопки и страницы той панели (gateway, curator, memory provider, portal, plugins hub, pairing...). Часть из них — ровно то, что вам нужно (Telegram, память, плагины, MCP). Часть — наследие, не имеющее смысла для ARIA. По вашему решению ни одной заглушки быть не должно, поэтому для каждой мы решаем: реализовать по-своему или удалить вместе со страницей.

## 5. Как вы будете этим пользоваться (целевая картина)

1. **Повседневно — через Telegram.** Пишете боту задачу голосом или текстом («собери сводку по заметкам за неделю», «разбери инбокс»). Бот отвечает, а на опасное действие присылает кнопки **Approve / Reject**. Ноутбук должен быть включён и приложение запущено (в трее, без окна).
2. **Окно приложения — пульт.** Настройки ключей и провайдеров, просмотр сессий и событий, граф роя, логи, подтверждения, правка навыков.
3. **Заметки (vault) — память и результат.** Каждая завершённая задача превращается в заметку с шагами, вызовами тулов и вердиктом честности. Открывается в Obsidian.
4. **Расписания.** «Каждое утро — дайджест», «каждую ночь — разбор инбокса»; результат приходит в Telegram.
5. **Навыки (skills).** Это инструкции для агента (`SKILL.md`). Новый навык = новая папка; агент подхватывает его при следующем запуске.

### Где что лежит на вашем компьютере
`[проверено 09.10]` в установленной версии (frozen) данные хранятся в папке пользователя: `%APPDATA%\ARIA` (там лежат `.env`, `logs\backend.log`) (при переменной `ARIA_DATA_DIR` — там). Внутри (по коду `paths.py`): `logs\backend.log`, `skills\`, `.env` (ключи) и база. Папка заметок (vault) задаётся настройкой `OBSIDIAN_VAULT_PATH`: её можно направить на ваш настоящий Obsidian-vault. В режиме разработки данные лежат в `backend\data`.

## 6. Словарь

| Термин | Простыми словами |
|---|---|
| Сайдкар | `backend.exe`, запускаемый окном как помощник |

| Аудит честности | Проверка кодом (без LLM), не соврал ли агент о результате |

| Skill | Папка с `SKILL.md` — инструкция для агента |
